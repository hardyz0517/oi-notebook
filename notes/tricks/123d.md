# 点分树常见实现坑
点分树本身的思想不算特别难，真正容易出问题的是实现细节。尤其是动态点分治题，代码通常同时维护原树信息、点分树父亲、距离结构和修改查询结构，任何一处下标或更新顺序错了都很难调。

最容易炸的是 **重心构建时的 vis 标记**。

找重心时不能让已经作为点分树节点的重心继续参与递归，否则子树会被重复拆分。`get_rt`、`get_sz`、递归建树这几步都要跳过 `vis[v] == true` 的点。

第二个坑是 **sum / root / best 的重置**。

每次找当前连通块的重心前，都要重新设置当前连通块大小 `sum`，并把候选重心和最大子树值初始化好。很多 WA 是因为上一层递归留下来的 `rt` 或 `mx` 没清空。

第三个坑是 **点分树父亲和原树父亲不要混用**。

原树上的 `fa` 常用于 LCA 或 DFS，点分树上的 `pa` 表示重心分治父亲。查询时沿着点分树父亲向上跳，不是在原树上跳。

第四个坑是 **距离一定要按原树距离算**。

点分树只是分治结构，两个点之间的距离仍然是原树距离。通常需要 LCA 预处理，查询 `dist(u, anc)` 时用原树深度和 LCA 算。

第五个坑是 **修改和查询要沿点分树祖先链更新**。

比如修改点 `u` 的颜色或权值时，要从 `u` 开始一路跳点分树父亲，把对每个重心的贡献更新进去。查询也类似，从 `u` 跳到所有点分树祖先并合并答案。

第六个坑是 **去重 / 容斥结构容易写错**。

有些题需要维护 `ans[x]` 和 `sub[x]` 两类结构，避免同一个子树贡献被算多次。比如动态距离和、最近黑点、颜色统计题，都要注意“来自哪个点分树儿子”的贡献是否需要扣掉。

第七个坑是 **复杂度常数不小**。

点分树每次操作一般是 `O(log n)` 个重心祖先，但如果每层还套 `multiset`、Fenwick、堆，常数会变大。不要在查询里做整棵子树扫描，否则会退化。

调试顺序建议：

1. 先检查点分树父亲是否建对。
2. 再检查每个点到点分树祖先的距离是否正确。
3. 再单独测一次修改是否更新了所有祖先。
4. 最后测查询是否做了正确的合并或容斥。

如果样例过了但大样例 WA，优先怀疑距离、容斥和重复贡献。
